# GBA Card Art — Technical Reference

## Current build

The production bake uses 8bpp art for all 1,809 non-energy cards. Energy cards
are generated by the engine and are not baked. The current ROM estimate is
about 29.1 MB after LZ77 compression, within the practical 32 MB cart limit.

| Asset | Format | Size |
|---|---|---:|
| Detail art | 96×144, 8bpp, 240-color palette | 14,308 B/card |
| Hand front | 24×32, shared palette | 768 B/card |
| Stage front | 34×48, shared palette | 1,920 B/card |
| Live front | 22×16, shared palette | 384 B/card |
| Waited front | 32×24, shared palette | 768 B/card |
| Shared master palette | 240 RGB15 entries | 484 B |

The active match loads only the cards needed by the selected decks into the
runtime set. ROM size is dominated by baked data; VRAM and palette limits are
the runtime constraints.

## Bit-depth tradeoffs

The baker supports 8bpp, 5bpp, and 4bpp output. The important discontinuity is
that 4bpp packs two pixels per byte, while 5bpp and above use one byte per
pixel. Palette reduction can therefore improve compression for the 8bpp path
without producing a proportionally small result.

| Mode | Approximate compressed ROM | Quality |
|---|---:|---|
| 8bpp / 240 colors | 29.1 MB | Production |
| 5bpp / 32 colors | 21 MB | Acceptable fallback |
| 4bpp / 16 colors | 10.3 MB | Basic |

The current constants live in `tools/bake_card_art.py`. Change them, rerun the
baker, and rebuild the GBA target rather than editing generated assets.

## Card ordering and deck-builder data

The GBA deck builder and web exporter share the Series → Rarity → Card order.
Measured D-pad savings across the baked deck set were 15% overall and 30–33%
for the bp7 ability decks. The builder provides hierarchical filtering,
quantity limits, legality feedback, deck-name entry, and eight SRAM custom
decks. Its implementation and current status are maintained in
[`output/GBA_PORT_NOTES.md`](output/GBA_PORT_NOTES.md).

## Why individual files instead of atlases

The 3DS uses texture atlases because PICA200 can decode compressed textures.
GBA has no equivalent texture decoder and uses direct per-card assets. The
runtime needs random access to arbitrary detail cards, 8×8 tile alignment, and
simple `include_bytes!` integration; an atlas would add indexing and loading
complexity without a GPU decode benefit.

## LZ77 contract

`tools/bake_card_art.py` emits standard BIOS LZ77 streams. Every `.bin` has a
`0x10` header followed by the little-endian decompressed size, even when
compression does not reduce the file. The master palette remains raw. The
runtime decompresses through the BIOS SWI 0x11 path for card fronts, detail
art, and UI assets.

The baker and runtime must be changed together. The LZSS gate validates the
stream before publication; a raw or malformed payload must never be passed to
the BIOS decompressor. This contract fixed the previous boot panic, jumbled
art, and silent garbage caused by mixed raw/compressed outputs.

## Build and regeneration

From the repository root, use the GBA build wrapper:

```bat
platforms\gba\build_gba.bat
```

The normal pipeline bakes deck data and card art before invoking the nightly
GBA build. For manual investigation, run `tools/bake_card_art.py` directly and
inspect the generated assets before rebuilding.

## Known caveats

- The current front-end uses text and focused-card detail; on-board fronts and
  richer zone highlighting remain future work.
- The 240-group text safety cap can truncate long lines.
- The production size figures are build measurements, not a promise for every
  future card corpus; rerun the baker and inspect the ROM after corpus changes.
- `pal_*.bin` files are embedded by the current asset set but are not consumed
  by the runtime; remove them only after checking the generated include graph.
