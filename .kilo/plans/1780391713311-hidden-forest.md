# Web Server Performance Optimization Plan

## Problem
Button presses take far too long to register/execute in the game UI.

## Root Cause Analysis

### Primary Bottleneck: Heavy work on both sides after every action
After a button press:
1. Frontend `GameService.sendAction()` POSTs to `/api/execute-action`
2. Backend:
   - Clones entire `GameState` under read lock for undo snapshot
   - Acquires write lock
   - Executes action via `TurnEngine::execute_main_phase_action()`
   - Calls `settle_single_player_state()` which loops through automatic phases
   - Calls `actions_with_index()` -> `generate_possible_actions()` (recalculates ALL actions from scratch)
   - Calls `display::game_state_to_display()` (serializes entire game state)
   - Returns large JSON response
3. Frontend receives response and:
   - Calls `updateStateData(data)` which does `JSON.parse(JSON.stringify(newData))` deep clone
   - Calls `rebuildCardIndex()` iterating every card in every zone
   - Emits change events that trigger full DOM re-render
   - Then fire-and-forget calls `State.fetchFrameCounter()` making another HTTP request

There is **no heavy polling loop causing the slowdown**. The `POLL_DELAYS`/`burst` constants are defined but I can't find any live polling timer in the active code paths. The delay is request/response bound: every action taxes both the backend (state cloning + full action generation + full serialization) and the frontend (deep clone + full card index rebuild + DOM rebuild).

### Secondary Factors
- `/api/execute-action` response includes both `game_state` and `legal_actions`; endpoints split them (`/api/game-state`, `/api/actions`) but `execute-action` still bundles both
- `settle_single_player_state()` in `web_server.rs` auto-advances through game phases; for complex board states this is nontrivial
- Locking: `std::sync::RwLock` plus broad lock scopes around clone/serialize blocks
- Frontend debug logging: `ActionListView.js` logs every action object to console, adding JS overhead on render

## Proposed Optimizations

### A. Remove Redundant Serial Round-Trips
**File: web_ui/js/services/GameService.js**
- `sendAction()` currently calls `State.fetchFrameCounter()` after every action (`GameService.js:103`), adding one unnecessary HTTP round trip. Remove or debounce that call.
- `State.update()` performs `JSON.parse(JSON.stringify(newData))` deep clone before applying data. Use structured clone or shallow merge where safe to avoid double-parsing.

### B. Frontend Rebuild Cost
**File: web_ui/js/state.js**
- `rebuildCardIndex()` rebuilds a lookup table over every card zone on every state update. Cache the index and invalidate only when `state_id` changes or relevant zones mutate.
- Reduce DOM churn in `ActionListView.js`: remove `console.log(JSON.stringify(...))` dumps that burn CPU/slow rendering on large payloads.

### C. Backend: Reduce Work Per Action
**File: engine/src/game/web_server.rs**
- Cache `legal_actions` in `AppState` alongside an invalidation flag. `execute_action` already knows the state changed; set `actions_dirty = true` and only regenerate when flag is set or a `/api/actions` request arrives.
- In `get_game_state`, skip `generate_possible_actions()` entirely and return cached `actions` together with the display.
- Drop the forced `settle_single_player_state()` auto-advance in `execute_action` when no phase change is needed; profile it first because it may be adding hidden CPU cost.

### D. Backend: Less Lock Time / Smaller Payloads
**File: engine/src/game/web_server.rs**
- Keep undo snapshot minimal rather than cloning the entire `GameState` under read lock before acquiring write lock.
- Consider returning a slimmer `GameStateDisplay` from `/api/execute-action` and leaving legal-actions fetch to the already-cached path.
- Serialize `UiConfig` once per request rather than locking `ui_config` inside the response builder.

### E. UI Feedback
**web_ui/js/components/ActionListView.js**
- Disable clicked action buttons immediately and show a lightweight "acting..." indicator using the existing `is_ai_thinking` pattern, so the user feels instant feedback while the backend finishes.

## Implementation Priority

1. **HIGH**: Remove `State.fetchFrameCounter()` after every action (cuts 1 extra HTTP call per press)
2. **HIGH**: Cache legal_actions backend-side (cuts the most expensive per-request CPU work)
3. **MEDIUM**: Stop console-logging full action objects in ActionListView
4. **MEDIUM**: Reduce `rebuildCardIndex()` work / cache card index
5. **LOW**: Evaluate slimmer execute-action response + undo snapshot optimization

## Risk Assessment
- Action caching is safe if invalidated only on mutation (execute_action, init_game, undo, redo).
- Dropping the redundant frame fetch is low risk; it is fire-and-forget today.
- No breaking API changes needed.
