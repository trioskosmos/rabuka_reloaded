# Plan: Audit Overengineered Ability Implementations

**Goal**: Identify ability-related code in the Rust engine that is architecturally overbuilt for the problem it solves, and outline targeted simplifications.

---

## Research Summary

I've read the core ability module (`engine/src/ability/`) and related files. Key observations:

### Overengineered Areas

#### 1. `ability/choice.rs` – 1950-line Mega-Function Pattern
`handle_select_card` is a ~1400-line function that branches on `zone` (Hand, Stage, Discard, LookedAt, Energy, ...) × `phase` (cost vs effect) with near-identical re-prompt logic duplicated per zone. Each zone handler re-implements: accumulate indices → re-prompt with remaining count → filter out invalid cards → store pending choice. This is classic copy-paste complexity accumulating over many card-specific fixes.

**What it actually does**: "Let the player pick N cards from a zone, applying type/cost/group filters, with support for sequential multi-pick."

**Over-engineering**: 6 copies of the same sequential-pick loop instead of a single generic `select_n_cards(zone, count, filter)` that handles re-prompting uniformly.

#### 2. `EffectPipeline` / `AbilityTraceNode` / `ZoneSnapshot` (in `types.rs`)
`ZoneSnapshot` captures 6 zone counts for **both players** and is built at every effect boundary. `EffectPipeline` redundantly stores `activating_card_id`, `selected_cards`, `moved_cards`—all already on `AbilityResolver`. `AbilityTraceNode` builds a tree of before/after snapshots for every sub-effect.

**What it actually does**: Provide debug-visible traces of how ability execution changes zone counts.

**Over-engineering**: The full trace tree pulls from production `GameState` and is almost certainly dead weight in normal test/play runs. The data is duplicated between `AbilityResolver.fields` and `EffectPipeline`.

#### 3. `execute_gain_ability_from_source` (in `ability_effects.rs`, ~120 lines)
Strips and copies abilities from under-member cards. Iterates every source card, then every ability on that card, doing string-based trigger filtering (`ability_trigger.contains(f) || f.contains(t)`). The result is stored as a `Vec<String>` in `gs.gained_abilities`, then re-matched at runtime.

**What it actually does**: Copy ability text from cards underneath a member to the activating card.

**Over-engineering**: The entire `gained_abilities` system is a runtime hack shadowing what `codegen_abilities.py` should handle at compile time. String-based trigger matching at runtime is fragile and slow.

#### 4. `AbilityResolver` Field Bloat (30+ fields)
Fields like `last_effect_target`, `last_effect_destination`, `last_effect_source`, `last_effect_position`, `pending_stage_cards`, `sub_choice_created`, `is_reveal_cost`, `last_draw_count`, `looked_at_total_count`, `selected_area` are one-shot state flags that create implicit coupling between unrelated handlers.

**What it actually does**: Thread state through the async/suspend-resume ability execution model.

**Over-engineering**: These are global mutable flags masquerading as structured state. They make it impossible to reason about which function reads/writes which flag.

#### 5. `SelectTargetKind` + `ChoiceRoute` + `Choice` Triple Dispatch
Three parallel routing systems (`SelectTargetKind::from_str`, `ChoiceRoute`, `ChoiceResult`) are used to select handlers. `handle_select_target` does 18+ string matches to route a single choice result. New choice types require adding a `SelectTargetKind` variant, a `ChoiceRoute` route, and a matcher arm.

**What it actually does**: Route a choice result to the correct handler function.

**Over-engineering**: A single `enum ChoiceKind { PrimaryAlternative, PositionChange, DrawAnyNumber, ... }` on `Choice` itself (which already has 7 variants) would eliminate 2 of the 3 routing layers.

## Proposed Plan Phases

### Phase 1: Extract Generic Sequential-Card-Picker (file: `ability/choice.rs`)

Refactor `handle_select_card` to extract a `select_cards_loop` helper that handles:
- Reading current zone by name
- Applying `CardFilter` 
- Managing accumulated indices and re-prompt loop
- Handling `allow_skip`, `is_reveal`, `blind`, `target_player`

Each zone handler becomes a 3-5 line wrapper calling the generic loop with zone-specific move logic.

**Risk**: High interaction with `effect_started` gating. Must preserve cost-phase vs effect-phase区别 exactly.

### Phase 2: Scope Down or Gate `EffectPipeline` / `AbilityTraceNode`

- Make `AbilityTraceNode` / `ZoneSnapshot` allocation conditional on a `debug_trace: bool` flag on `AbilityResolver`.
- Remove the duplicated fields from `EffectPipeline` (`activating_card_id`, `selected_card_ids`, `moved_cards`) since they live on `AbilityResolver` already.

**Risk**: Tests that assert on `pipeline.trace.children` will break. Need to audit test fixtures first.

### Phase 3: Collapse `gained_abilities` String Storage to Compiled Ability Refs

Replace the `HashMap<i16, Vec<String>>` `gs.gained_abilities` with structured data (or resolve at compile time via `codegen_abilities.py`). The runtime string check in `execute_gain_ability` can become a direct call if the compiler already generated a hardcoded entry.

**Risk**: Touches the hardcoded bypass path. Must run `codegen_abilities.py` after every change.

### Phase 4: Consolidate Resolver Fields

Move `last_effect_target/destination/source/position` into a small `EffectSpawnContext` struct. Move `is_reveal_cost`, `last_draw_count`, `looked_at_total_count`, `selected_area` into local state or `GameState` where appropriate.

**Risk**: `AbilityResolver` is passed around liberally; field renames affect many call sites.

### Phase 5: Merge Choice Routing Layers

Replace `SelectTargetKind` + `ChoiceRoute` + string matching with a single `ChoiceKind` enum on the `Choice` variants. Reduces `handle_select_target` from a 70-line match cascade to a direct function dispatch.

**Risk**: `ChoiceCardNo` is serialized to JSON for the frontend; restructuring the enum needs frontend coordination.

---

## Execution Order Recommendation

1 → 2 → 4 → 3 → 5

Phase 1 (generic picker) has the highest complexity reduction / risk ratio. Phase 2 removes memory bloat from hot-path tests. Phase 4 improves readability. Phase 3 is risky because it touches the hardcoded/compiled path. Phase 5 is a cleanup that depends on 1-4 being complete.

## Test Scope Gap Analysis

### How QA Coverage Currently Works

1. `cards/qa_card_list.md` — human-maintained manifest mapping QA IDs → card numbers → test filenames. 159 rows. Several rows have blank test filenames (untested).
2. `cards/qa_data.json` — source of truth. ~4000 QA entries with `id`, `question`, `answer`, `related_cards`.
3. `engine/src/qa_test_suite.rs` — ~2654-line binary that calls `run_all()`. Some entries have Rust test functions, others are unimplemented stubs that just `println!` the QA text. **Not wired into `cargo test`.**
4. `engine/tests/run_qa_tests.rs` — test harness that calls `rabuka_engine::qa_test_suite::run_all()`. Does NOT assert pass/fail; it just runs output.
5. `engine/tests/test_modules/remaining_quick_test.rs` — real gameplay tests for Q203, Q204, Q218 using full `TestGame` helpers.

### Problem: Q257 and 桂城 泉 (PL!HS-bp6-008)

The user's snippet shows:
- **Q257**: "When this member debuts, if there is no matching live card in your waitroom, must this member go to wait?" → Answer: **Yes, always becomes wait.**
- **Card data**: `PL!HS-bp6-008-R` and `PL!HS-bp6-008-P` both run the same `ab#0`.
- **Ability text**: `登場：このメンバーをウェイトにする。その後、自分の控え室からスコア4以下の『蓮ノ空』のライブカードを1枚手札に加える`
  - Step 1 (mandatory): this member → wait
  - Step 2 (conditional on waitroom having match): from waitroom, score ≤ 4 蓮ノ空 live_card → hand (1 card)

**What's missing**:
1. No row in `qa_card_list.md` for `PL!HS-bp6-008`. → Q257 is **untracked** in the manifest.
2. `qa_test_suite.rs` has a stub for Q257 that only prints the answer; it does not compile or assert.
3. The 2-step `sequential` with mandatory `change_state: wait` followed by a conditional `move_cards` from discard is an **untested engine pattern** — no existing test covers a sequential where step 1 is unconditional state change and step 2 is a group+cost combined filter from discard.

### What Tests Should Cover

**For Q257 specifically (桂城 泉)**:
- **Case A (waitroom empty)**: Debut with no matching live cards in waitroom → card becomes wait, no second effect runs, no crash.
- **Case B (waitroom has matching card)**: Debut with 1× score-4 蓮ノ空 live in waitroom → card becomes wait AND that live card moves to hand.
- **Case C (waitroom has non-matching card only)**: Debut with only score-5 蓮ノ空 live OR non-live in waitroom → card becomes wait, no second effect, no crash.
- **Case D (multiple matching cards)**: Debut with 2× matching cards in waitroom → player prompted to choose 1.

**For the QA framework in general**:
- `qa_test_suite::run_all()` must produce a structured machine-readable report (`PASS`/`FAIL`/`SKIP` per QA ID) so the infra can compute coverage delta.
- Binary should distinguish: untested stub, tested-pass, tested-fail, engine-crash.
- The report should feed back into `qa_card_list.md` status column.

Change `qa_test_suite.rs` from `println!` stubs to `assert!`-based tests with a `Vec<(QA_ID, Result)>` accumulator. Produce JSON report `reports/qa_run_report.json`. Wire into `tests/run_qa_tests.rs` so results count as test outcomes.

**Risk**: Existing binary that only prints needs new `use` paths and the report write needs directory creation.

- Q191 (Daydream Mermaid): modify_required_hearts with heart color restriction — verify modifier applies only when hearts match selected color.

**Risk**: Medium. These are new gameplay tests using existing helpers, low coupling.
