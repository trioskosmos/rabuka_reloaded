# Plan to Speed Up `cargo t` in engine folder

## Observations
1. The test suite uses a helper module (`tests/helpers`) that provides `TestGame` and `load_real_database`.
2. `load_real_database` uses `OnceLock` to load the card database once per process, which is efficient.
3. However, each test creates a new `TestGame` instance, which does the following expensive operations:
   - Creates two players and a fresh `GameState`.
   - Pre-creates a copy pool for every card template in the database (iterates over all cards and creates one copy per template).
   - Enables ability debug logging (which may cause overhead due to locking and `eprintln!`).
4. The number of cards is large (cards.json ~2.9MB, abilities.json ~1.3MB), so iterating over all card templates per test is costly.
5. The current `cargo t` alias runs tests sequentially (`--no-fail-fast` but without explicit test thread control).

## Proposed Changes
### 1. Improve Test Parallelism
Update the cargo alias in `.cargo/config.toml` to enable parallel test execution:
```diff
[alias]
- t = "test --no-fail-fast"
+ t = "test --no-fail-fast -- --test-threads=0"
```
This will use all available CPU cores to run tests in parallel, significantly reducing total execution time for multi-core systems.

### 2. Optimize TestGame Setup (Optional, requires careful consideration)
If further speedup is needed, consider modifying `TestGame::new` to reduce per-test overhead:
- **Lazy copy pool initialization**: Instead of pre-creating copies for all card templates, create copies only when `id()` or `new_id()` is first called for a given template. This avoids the upfront iteration over all cards.
- **Selective pre-creation**: Allow tests to specify which card templates they need copies for, reducing the number of copies created per test.
- **Note**: These changes would modify `tests/helpers/mod.rs` and potentially require updates to tests that rely on the current behavior (e.g., tests that expect unique copy IDs for many cards). Since the user prohibited touching debug lines but did not prohibit other changes, this is acceptable if debug-related code remains untouched.

### 3. Evaluate Debug Overhead
The `TestGame` constructor enables debug logging and flushes it in `Drop`. If debug output is not required for a test's assertions, consider:
- Making debug enabling configurable per test (e.g., via an argument to `TestGame::new`).
- However, avoid changing any debug-related code (e.g., `ability::debug.rs`) as per user request.

### 4. Alternative Test Runner
Consider installing and using `cargo-nextest`, a faster test runner for Rust:
```bash
cargo install cargo-nextest
```
Then use `cargo nextest run` instead of `cargo t`. This can provide significant speedups due to smarter test scheduling and isolation.

## Implementation Steps
1. Update `.cargo/config.toml` with the new alias (Step 1).
2. Measure the improvement in test execution time.
3. If further improvement is needed, proceed with Step 2 (lazy copy pool) after evaluating impact on existing tests.
4. Optionally, document how to use `cargo-nextest` for even faster test runs.

## Notes
- The changes in Step 1 are safe and only affect test execution parallelism.
- Steps 2 and 3 involve modifying test helper code but avoid debug-related lines as requested.
- Ensure that any changes to `TestGame` maintain the same interface and semantics for existing tests.
