# Engine Optimisation & Bottleneck Analysis

## Executive Summary

The engine is functionally solid but has several performance and maintainability bottlenecks. The dominant issues are **excessive cloning**, **allocation-heavy string processing**, and **monolithic state snapshots**. These compound during simulation/benchmarking and under web server load.

---

## High-Impact Issues

### 1. Deep-cloning `GameState` everywhere (Critical)

`GameState` derives `Clone` and contains ~60 fields including `Vec`, `HashMap`, `HashSet`, `String`, `Vec<LogEntry>`, `Vec<PerformanceSnapshot>`, `ResolutionZone`, and nested `Player`. It is deeply cloned in the web server on every history/future snapshot push:

- `engine/src/game/web_server.rs:309` — `data.game_state.clone()`
- `engine/src/game/web_server.rs:585` — `data.future.lock().unwrap().push(game_state.clone())`
- `engine/src/game/web_server.rs:609` — `data.history.lock().unwrap().push(game_state.clone())`

A single clone likely allocates and copies dozens of `Vec`s and `String`s. For a 1-hour play session this accumulates.

**Recommendations:**
- Replace O-O clone-full-state history with `Arc<RwLock<GameState>>` + an **event log / command pattern** that can replay deltas.
- If snapshots are required, store `Arc<GameState>` and only clone on divergent branch points (future navigation).
- Consider `Rc<RefCell<>>` for single-threaded hot paths to avoid `RwLock` overhead where concurrency isn't needed.

### 2. `String` explosion — 449 `.to_string()` calls (High)

Strings are the primary alloy type in the engine, used for card numbers, zone names, ability keys, player IDs, phase names, action strings, etc. Key hot-path culprits:

- `engine/src/ability/condition/state.rs` — every condition evaluation allocates strings for target resolution and phase matching.
- `engine/src/ability/util.rs` — `calculate_play_cost_reduction` searches stage, success live, and card DB in nested loops, building strings on each iteration.
- `engine/src/ability/effects/mod.rs:71` — `replacement_effects.iter().map(|r| (*r).clone()).collect()` clones the full vector; combined with string keys for `non_stackable_effects`.
- `engine/src/ability_queue.rs:142` — `has_entry_with_id` does linear scan with `String` equality on every enqueue.
- `engine/src/turn/actions.rs:186-188` — `format!("{}_{}_{}", card_id, idx, game_state.turn_number)` creates turn-limited keys every activation.

**Recommendations:**
- Intern stable strings (`static ONCE_CELL` / `FxHashMap<String, u32>` or `string_interner` crate). Card numbers, phase names, and ability action strings are natural candidates.
- Replace `AbilityId` (currently `String`) with a small struct of `(CardNo: u32, idx: u8, trigger: u8)` using the existing card database ID space.
- Replace `String` player IDs with `PlayerId(u8)` enum/struct.
- Replace `format!` keys in `turn_limited_abilities_used` with a tuple or hashed enum.

### 3. Clone-heavy API surface — 663 `.clone()` calls (High)

Beyond `GameState`, cloning occurs in:

- **QA test suite** (`engine/src/qa_test_suite.rs`) — clones card database for every single test case (~20+ tests).
- **Card loader** (`engine/src/core/card_loader.rs:94`) — `ability_map.entry(...).or_insert_with(Vec::new).push(ability.clone())` clones abilities per card. `Ability` derives `Clone` but EffectPipeline/AbilityEffect trees are deep.
- **Resolver** (`engine/src/ability/resolver.rs:10`) — `AbilityResolver` is cloned when stored in `AbilityQueueEntry`.
- **Web server** — entire `GameState` cloned into `FrameSnapshot` fields via `active_player().id.clone()` and card name clones per action.

**Recommendations:**
- Use `Arc<CardDatabase>` (already done) but avoid `.clone()` on it where `&CardDatabase` suffices.
- Use `Cow<'_, str>` or `&'db str` for card text loaded at startup, with the database as the backing store.
- Pass `&Ability` instead of `Ability` where possible.
- In `CardLoader::attach_abilities`, avoid cloning abilities into per-card vectors; use `Arc<Ability>` or direct indices into a global ability slab.

### 4. Condition evaluation is string-heavy and repetitive (High)

`ConditionContext::evaluate_condition` and friends in `engine/src/ability/condition/state.rs`:

- Phase matching uses `matches!(..., Phase::X)` but `temporal` and `phase` are `&str`/`Option<String>` and compared via string matching every evaluation.
- `resolve_condition_player` is called repeatedly for the same target strings.
- `card_matches_count_filters` likely performs repeated `HashMap` lookups by `String` group names.
- `text.contains("登場")` and `text.contains(condition.text)` appear in hot condition branches.

**Recommendations:**
- Parse conditions into a typed enum on load (or at `GameState::new`) so evaluation becomes enum dispatch instead of string matching.
- Cache `resolve_condition_player("self")` / `resolve_condition_player("opponent")` results per evaluation pass rather than recomputing per condition.
- Replace `String` group names / action names in `Condition` with interned IDs or small enums.

### 5. `calculate_play_cost_reduction` does 3 full scans of stage+live (Medium)

`engine/src/ability/util.rs:31-152` scans:

1. The card's own abilities.
2. Every stage member's abilities (up to 3).
3. Every success live card's abilities.

Each inner loop calls `ActionType::from_str`, `effect.operation == Some("subtract")`, `Zone::from_str`, and `card_matches_group_str` — none of which are pre-parsed.

**Recommendations:**
- Pre-index cost-reduction abilities by card ID at database load time (a `HashMap<i16, Vec<CostReduction>>`).
- Use an enum `CostReductionKind { Hand, Stage, Live }` to avoid re-parsing `location` strings.
- Short-circuit: if stage[0] yields a reduction, skip stage[1] and stage[2] and skip live entirely.

### 6. Web-server `GameState` round-trip overhead (Medium)

`FrameSnapshot::capture` (`engine/src/game/web_server.rs:52`) constructs a new struct every frame by iterating vectors and cloning card IDs (`iter().copied().collect()`). Meanwhile `GameStateDisplay` (likely much larger) is also serialised in `GameStateResponse`.

- `engine/src/game/web_server.rs` has 20+ `.clone()` calls on `game_state` itself per request cycle.
- `generate_possible_actions` is called twice per benchmark loop iteration (`run_single_game_to_completion`).

**Recommendations:**
- Serialize `GameState` directly via `serde` with `#[serde(skip_serializing = ...)]` on transient tracking fields rather than building `GameStateDisplay`.
- Make `FrameSnapshot::capture` write into pre-allocated buffers or use `SmallVec<[i16; 12]>` for hand/discard so `collect()` doesn't allocate.
- Cache `card_no`/card name strings in the `Player` or a dedicated display cache so serialisation doesn't re-query `CardDatabase`.

### 7. `AbilityQueue` is linear scan with `String` IDs (Medium)

`AbilityQueue` stores entries in `Vec<AbilityQueueEntry>` and uses `current_index` to walk. `has_entry_with_id` does `.iter().any(|e| e.id == *id)` — O(n) with `String` equality.

**Recommendations:**
- Use `IndexSet<AbilityQueueEntry>` or `Vec` + `FxHashMap<AbilityId, usize>` for O(1) dedup checks.
- Replace `AbilityId` with a `u64` hash or small struct as noted above.
- Remove the `dummy_entry` creation in `pause_for_choice` when state is `Idle` — re-architect so choices attach to the current entry without fabricating an empty `Ability`.

### 8. Memory / allocation hygiene in benchmarks (Low–Medium)

`engine/benches/performance.rs`:

- `setup_full_game` loads `cards.json` from disk on every benchmark invocation unless cached externally. The `OnceLock` at module scope is never used in the shown code.
- `run_games_for_duration` clones deck templates — which contain `Vec<String>` — per iteration.

**Recommendations:**
- Use the global `OnceLock<Arc<CardDatabase>>` and `OnceLock<Arc<Deck>>` for benchmarks.
- Store deck card numbers as `Vec<u16>` / `Box<[u16]>` instead of `Vec<String>` to reduce per-card allocation during benchmark setup.

## Low-Impact / Hygiene

- `recursion_limit = "512"` in `lib.rs` — verify this is actually needed; if recursive types can be flattened, lower it to reduce compiler pressure.
- `game_state_history: Vec<String>` stores stringified snapshots; if used for debugging only, gate behind `cfg!(debug_assertions)` or swap to `Option<String>` batch-writer.
- `performance_snapshots: Vec<PerformanceSnapshot>` — confirm whether this is consumed or sentinel data; if the latter, use `Option<Box<[PerformanceSnapshot; 8]>>` or a smallvec.
- `#[derive(Debug)]` on every large struct adds bloat to debug builds; gate behind `cfg(debug_assertions)` if compile times are suffering.

## 1. `game_state_to_display()` String Churn (High)

`display.rs:112-160` (`card_to_display`):
- `card.card_no.clone()`
- `card.name.clone()`
- `card.ability.clone()` (full ability text, potentially huge)
- `format!("{:?}", card.card_type)` — allocates every call
- `base_heart` HashMap rebuild per card
- `orientation.map(|o| format!("{:?}", o))` — allocates per card

Called via `game_state_to_display()` at 11 sites in `web_server.rs`:
- `ws_index`, `ws_execute_action`, `undo`, `redo`, `settle_single_player_state`,
  and several others.

Every HTTP response for the UI rebuilds this from scratch. For a hand of 5, stage of 3,
discard of 10, that's ~20 card DB lookups + 20 `String` clones per request.

**Fix: `CardDisplay` should borrow from `CardDatabase` rather than clone strings.**
- Add `card_db: &CardDatabase` to callers and pass it through.
- In `CardDisplay`, replace `card_no: String`, `name: String`, `ability_text: String`
  with `card_no: &'db str`, `name: &'db str`, `ability_text: Option<&'db str>`.
- Pre-compute card_type/orientation as `&'static str` at database load time via
  `lazy_static` / `OnceLock` maps, so no `format!` allocation.
- Make `base_heart` reuse the `HashMap` from `CardDatabase` (it's already stored there).

Alternatively, if `serde` serialization of `&'db str` causes trouble with the
`'static` lifetime in JSON responses, cache a `RwHashMap<i16, CardDisplay>` per
`GameState` and only invalidate on real board mutation.

**Fix: Skip display rebuild when nothing changed.**
Cache the last `GameStateDisplay` and a `dirty` flag set only in `execute_action`.
Many web endpoints read the display without any state change.

## 2. QA Test Suite Pointless Cloning (Medium)

`qa_test_suite.rs`: ~20+ `GameState::new(player1, player2, card_database.clone())`
calls. `card_database` is already `Arc<CardDatabase>` — `.clone()` is an atomic
refcount increment, cheap, but completely pointless. Change to `&card_database`.

## 3. Condition Eval String Parsing (Medium)

Hot paths in `ability/condition/state.rs`:
- `ActionType::from_str(&effect.action)` on every effect check
- `Zone::from_str(...)` in multiple evaluators
- `phase == "active"` style string matches
- `condition.text.contains("登場")` — scans full text string every evaluate

**Fix: Pre-parse `Condition` into a `ConditionKey` enum on attachment to card
or on first evaluation. Cache in `ConditionContext` where possible.**

Short-term: add a `lazy` module once.
Mid-term: `Condition` gets a `parsed: OnceCell<ConditionEnum>` field.

---

## 4. `calculate_play_cost_reduction` Triple Scan (Low-Medium)

`ability/util.rs:31-152`: scans own abilities → stage → success_live, each doing
`ActionType::from_str` + `Zone::from_str`.

**Fix: Build a `HashMap<i16, CostReduction>` at database load time. Keys are
card IDs; value encodes location (Hand/Stage/Live) and reduction amount.**
`calculate_play_cost_reduction` becomes 3 HashMap lookups.

Also: drop the `card_type != "member_card" && card_type != "card" && ...`
guard — cost reduction abilities are already on member cards by convention.

## Concrete Implementation Steps (What to do first)

### Step A — Fastest win: stop cloning strings in display (target: `display.rs`)

1. `display.rs` `CardDisplay`: change name/card_no/ability_text/types/orientation
   to borrowed `&'db str` lifetimes.
2. Add `'db` lifetime to all display structs.
3. Update `game_state_to_display` to take `&CardDatabase` and emit borrowed data.
4. Update all 11 call sites in `web_server.rs` to pass `&game_state.card_database`.
5. Serde handles `&str` fine for JSON output (it serializes as borrowed).

### Step B — `calculate_play_cost_reduction` index (target: `ability/util.rs` + `card_loader.rs` + `card.rs`)

1. `CardDatabase` gains `cost_reduction: HashMap<i16, Vec<CostReduction>>`.
2. Populate in `CardLoader::attach_abilities` by scanning for `modify_cost/subtract`.
3. `calculate_play_cost_reduction` reads from index instead of scanning cards.

## What NOT to do

- **Don't delta-encode history/future.** It's not needed.
- **Don't intern every String yet.** Do the display fix + cost index first and measure.
- **Don't rewrite the ability system as enum dispatch** until after measurement shows
  condition parsing is hot (it probably is, but confirm with criterion first).
